## Description
In Development and Test, API startup applies migrations and creates the fixed cast from workflow.md section 7 ("Seeded development data"): 4 workers (3 approved, 1 pending), 5 clients, 1 admin, with their trades, coverage and home neighborhoods, plus three sample jobs that put the app into the states we demo and test most (open job with bids, open job without bids, finished job waiting for ratings). Each seeded user exists in Supabase Auth and in `app.users` with the same id, and signs in locally with code `123456`.

## Stories
- US-0003 Seeded users can sign in locally
- US-0004 Seeder runs only where it is allowed
- US-0005 Seeded workers have trades, coverage and approval state
- US-0006 Sample jobs are seeded once

## Business rules
- Development (and Test) only, with `Seed:Enabled`; never Production (workflow.md section 7, slice 2).
- Seeded users are created through the Supabase Auth admin API with a confirmed phone; an existing auth user with the same phone is reused (workflow.md section 7, slice 2).
- `DevUsers` and the `[auth.sms.test_otp]` numbers in `supabase/config.toml` match exactly (workflow.md section 7, slice 2).
- Sample jobs are added only when no jobs exist (workflow.md section 7, slice 2).
- Worker coverage is stored at neighborhood level (workflow.md section 1, Location).
- Credentials go to the git-ignored `docs/local-credentials.md`; nothing secret is committed (workflow.md section 1, Local data).
