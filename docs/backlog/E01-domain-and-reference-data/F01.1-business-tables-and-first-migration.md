## Description
One migration, replacing today's empty `Initial`, creates every business table from workflow.md section 3 in schema `app`, with RLS enabled on each table and no policies, so only the API can read or write business data. The database itself refuses the duplicates that would break core rules: two bids by the same worker on one job, two ratings by the same person on one job, two accounts with one phone, two stores with one referral code, two jobs with one number.

## Stories
- US-0011 Business tables exist in a locked-down `app` schema
- US-0012 The database refuses duplicates that break core rules

## Business rules
- All tables in schema `app`; no foreign keys into Supabase's `auth` or `storage` schemas, so migrations run on plain Postgres (workflow.md section 3).
- `app` is not exposed through the Data API and has RLS enabled with no policies (workflow.md section 1, Database; `.claude/rules/backend.md`).
- Money as whole RSD; all times UTC (workflow.md section 1, Database).
- One bid per worker per job, unique `(job_id, worker_id)` (workflow.md section 2, Business rules).
- One rating per rater per job, unique `(job_id, rater_id)` (workflow.md section 3).
- `app.users.id` equals the Supabase auth user id (workflow.md section 3).
